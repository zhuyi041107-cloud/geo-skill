# 按原模板生成整套客户交付

这是WorkBuddy必须执行的完整生成说明。用户指定的原模板是交付标准；先完成同等结构、表格和业务颗粒度，再考虑后续调整。原模板中的公司、案例、篇数、报价和平台机制不是本项目事实。模板的章节与表头以 `template-contract.json` 为准，写作判断以本文件为准，排版与命令见 `pdf-output.md`、`commands.md`。

## 目录

1. 先建立一份贯穿所有文件的项目底稿
2. 诊断模板：平台型业务
3. 诊断模板：项目或服务型业务
4. 执行方案：从缺口一直写到逐篇生产表
5. 约2万元预算如何编排
6. 推荐媒体Word与Excel如何对应
7. 导出前逐项验收

## 1. 先建立一份贯穿所有文件的项目底稿

收到任意一个平台的回答，就用该轮材料完整生成。已有判读、答案和截图直接复用。内部先完成以下底稿，随后写报告，不先向同事交一份处理过程：

| 内部底稿 | 必须形成的业务信息 | 成稿用途 |
| --- | --- | --- |
| 客户事实卡 | 品牌、运营/商标/产品主体各自关系；核心服务；客群；地域；资质与适用边界；真实案例；收费和官方渠道。逐项区分客户自述与已公开证据 | 主体说明、可信事实、统一写作口径 |
| 需求与回答卡 | 每个真实问题问的是什么选择；答案实际推荐谁、如何描述品牌；截图可见来源；已知和未知 | 路径状态、场景矩阵、竞争依据 |
| 竞争与来源卡 | 实际出现的候选主体、被描述的理由、承载内容的网站/账号；本品牌有无相应事实和可见承载 | 竞品表、信源表、机会判断 |
| 缺口—任务表 | 每个缺口对应的目标用户/问题、要形成的认知、事实材料、文章与页面、媒体角色、首次检查点 | 执行目标、选题、客户动作 |
| 生产与费用表 | 每篇独立内容、每次刊发的具体媒体/单价/数量/日期、阶段、自然季度和费用范围 | PDF、内外Excel、媒体Word共同取数 |

先用客户资料和本轮观察选择模板：双端平台、交易/招聘/渠道平台等，采用 `platform`；按项目评估交付能力、地点条件、配套、报价和案例的业务，采用 `service`。选择的是最接近客户决策的原版结构，不能只换行业名。

客户报告不写底稿如何建立、导入步骤、算法流程或“怎么诊断”。本轮范围只简短给出实际平台和日期。原模板的流程图讲的是客户如何选择服务，不是智能体如何工作，应当保留。

每一段按“可见情况 → 业务判断 → 对选择的影响”展开；每一张表前给出这张表要说明的主要情况，表后说明优先取舍。缺乏原因证据时写观察与策略假设，不把假设写成已证明原因。

### 把完整内容组装成report.json

1. 写 `template_profile=platform` 或 `service`，再为diagnosis、execution分别写summary与sections。使用对应profile的完整章节顺序和标题层级；不能将两个参考结构拼成另一套泛章。
2. 每节写key、title、paragraphs和tables。paragraphs使用title/detail，可加内部evidence_ref；说明本节的客户情况、表格体现的差异和取舍，不重复同一套宣传段落。
3. `source=report`的表用契约里的id与原样columns，rows逐行填本案内容，列数准确，必需矩阵非空。未确认字段只在局部写清边界，不删除整个章节或捏造检测结论。
4. `source=plan`的表由plan/analysis生成，不在report手写另一套数量与金额。对应章节的paragraphs解释为什么这样安排。阶段目标放stages，具体标题/问句/事实/日期放contents，实际媒体/次数/单价放placements。
5. `source=diagnosis`的执行路径直接复用诊断同节，不独立改写成不一致的状态。诊断与执行中的同一个事实、需求与阶段引用保持对应。
6. 完整的结构参考随包report.example.json及同源project/plan例子。示例客户是虚构，不抄其业务结论。依赖脚本的校验结果逐项修正遗漏，直到生成的是完整原模板，而不只是格式正确的空骨架。

## 2. 诊断模板：平台型业务

按原平台型诊断的顺序生成，不能改成几章同构长段落。各表的行数由客户和本轮证据决定。

### 2.1 报告首页与核心判断

写客户品牌、业务赛道、报告日期和本轮平台范围。首页核心判断必须回答：点名能否识别、真实需求下能否进入候选、最影响业务的场景缺口、目前来源由谁承载、首先应统一或补齐什么。用本轮具体观察支撑；不以点名回答成功推断有多少人知道品牌。

首页的数字、平台、周期与执行文件一致。把有限的证据边界放在相关判断旁，正文主位用于情况分析，不重现原模板整页方法声明。

### 2.2 用户决策路径与四层应答情况

保留“产生需求 → 建立品牌意向 → 评估合作细节 → 比较替代方案”的路径，分别填本业务真实问法与品牌当前被呈现的位置。B端/C端有不同目的时分开说明，不把两个客群混成一个提及率。

下接认知、推荐、决策、定义四层。每层写明：这一层的用户关心什么；本轮具体呈现；能支持该判断的问句/回答；当前状态；业务含义。定义层是行业分类与选择标准，不是必须额外采一道科普题。未覆盖的层可用已有材料说明边界，不能编造一次检测。

### 2.3 一、品牌现状

先给连续判定段，再保留三项总判定：能否被识别、能否讲清业务、品类需求下的位置。表头保留“判定项 / 直询结果 / 说明”。说明要写实际服务、对象和场景，而不只写“有/无”。

自然需求与点名认知分开；推荐与通用核验知识分开。AI说出品牌名称但说错运营、收费或服务承诺，应同时呈现识别结果与事实问题。

### 2.4 二、品牌当前现状：客户场景对照

先用“客户关注场景 / 本品牌 / 指定竞品”给出状态矩阵，再用“客户关注场景 / 对应问句示例 / 本品牌提及 / 指定竞品提及 / 说明”解释。

每一行写真实问句、可观察出现情况和选择理由。竞品列写清实际主体及出现情境，不能用“竞品均已出现”掩盖不同回答。并列清单不是排名；通用决策题未点名品牌不是一次推荐失败。把本轮场景差异解释成客户选择入口的差异。

### 2.5 三、竞品现状

保留“对标主体 / AI引用依据 / 本主体对应情况”。这里比较的是对方靠哪些内容或事实进入选择，本品牌是否有相应能力和承载，不是主观打榜。

每个对标主体至少说明：本轮在哪种问题出现；回答强调什么；可见来源属于什么内容；本品牌相对应的已有事实、表达或缺口；应采取的内容动作。未见正文时按可见来源表述，不能把来源标题写成已核验背书。

### 2.6 四、信源层级覆盖矩阵

保留“信源层级 / 覆盖状态 / 覆盖质量 / 是否被AI实际引用”。按原四组承载角色归类：央媒/政务/协会，行业/专业内容，官网/百科/官方公示，社区/口碑/应用上架等。它是方案的内容分工，不是AI官方权重。

覆盖状态来自客户可见资产，实际引用来自本轮回答/截图，两者分别填。看不到的资产填本轮未确认，不能以未被引用断言全网不存在。应用商店是第三方平台承载，企业自己填写的介绍不自动变成独立第三方评价。

矩阵后指出需要补的是哪类事实或独立内容，如何服务哪个需求，不以同稿铺站数量代替多份独立佐证。

### 2.7 五、建议可增加的推荐场景

保留“建议新增场景 / 对应问句示例 / 建议理由 / 优先级”。每条理由写全三个判断：竞争或内容空档是什么；客户靠什么真实能力承接；为什么接近用户的选择或咨询动作。

这一节是内容机会清单，不自动变成下一轮人工采样任务。不能为了填满表格拓展客户没有能力的城市、业务或承诺。行数由真实机会决定，不复制原案例的场景数量。

### 2.8 六、优化建议与品牌心智标签

先按影响和先后依赖排优先级，再写“序号 / 得分项 / 说明”。这里的得分项是可改善的内容任务，不是保证提升AI分数。说明具体到页面、字段、稿件、可确认事实和检查结果；不能只写“完善官网、加强宣传”。

保留标签对标表“同类主体当前被贴的标签 / AI回答里对应的说法 / 本主体是否具备 / 建议动作”。再写“建议抢占的标签 / 一句话定义 / 支撑事实 / 落到方案里的哪类文章”。标签必须符合实际能力，并能在执行排期中找到对应内容与周次。

诊断最后用一段话说明哪几项先做、分别进入执行方案的哪个阶段。不能引用不存在的章节、阶段或文章。

## 3. 诊断模板：项目或服务型业务

沿用相同的首页、用户路径和四层应答框架，随后保留原项目型模板的业务评估结构。

### 3.1 品牌现状、购买路径与优先结论

梳理客户从产生项目需求、寻找服务、判断适配、比价到接洽的选择链。说明每一层目前能够回答什么、哪类决策证据不足、对报价或成交沟通有什么影响。摘要和业务影响先行，再进入矩阵。

### 3.2 信源矩阵与主体事实卡

按上节四类角色给出来源覆盖与引用状态，配主体事实卡，集中列主体、品牌/产品、区域、官方渠道、已知服务及事实来源。不同地址、法人、商标或历史主体之间的关系先区分，不自动认定冲突。

### 3.3 逐个业务维度做完整诊断

依据真实购买标准选择并命名维度。原模板的资源条件、属地交付、配套服务、价格透明、平台能力、案例可信、主体一致性是参考含义；别的行业要换成真实采购标准。

每个维度保留原四栏：评分说明、现有AI可查内容、AI缺失关键信息、AI应答现状。每栏要有本客户信息，不用同一段“建议补充”重复填充。缺失信息只指当前材料/观察不足，不能断言网络上不存在。

评分有明确定义与证据才写；否则该栏给业务判断及依据，写明未做量化评分。禁止随手编出3/5或精确提升分值。

### 3.4 风险与曝光场景

对事实归属、价格与适用条件、案例授权、信息陈旧或服务边界等实际风险，分别写当前表现、业务后果、影响的用户场景和处理动作。曝光盘点列实际被承接和未承接的需求，区分知名度目标与GEO回答目标。

### 3.5 目标问题、文章标题与内容规范

每组需求写真实目标问句、需要的事实、内容方向和具体拟发标题。标题之间必须有新增信息，不能一稿同义改写。原标题示例中“每组两篇”是案例配置，数量由真实信息增量、媒体角色和预算共同推导，不反过来凑问题。

写出本客户行业口径、事实字段、引用/案例授权和适用条件。把每个需求与实际文章、信源角色、阶段和费用连起来，最后解释为什么形成当前生产规模，不能只给一个总篇数。

## 4. 执行方案：从缺口一直写到逐篇生产表

两种业务都必须写到这一程度。按照所选原模板的章序与表头组织，不压缩成泛泛的“目标、媒体、预算”摘要。原模板的经验规则或确定性平台机制，改为本案策略和可验证的目标。

### 4.1 决策首页与执行总览

首页给客户、本轮范围、项目周期、独立内容篇数、刊发次数、阶段、费用与主要目标。所有数字来自同一plan，和文末排期逐行相加一致。

复用诊断中的用户路径和四层状态，保持两份文件对同一现状的描述一致。执行总览表保留“项目目标 / 主要工作 / 首次检查”。目标覆盖品牌知名度/正面形象及GEO需求入口，不能擅自排除其中一项。

首次检查应晚于相应素材、页面和稿件的实际到位日期。现有任务是生成方案，后续检查是执行计划内容，不是要求同事现在补平台或重采答案。

### 4.2 平台内容定位与统一执行原则

只写本轮实际平台及其回答体现的内容需求。用“平台 / 内容定位 / 依据与策略”解释选题与形式，不能复制“平台固定偏好”“几个月不更必降权”等未经证实机制。

统一原则要落到本项目的事实、内容分工和交付边界：主题服务哪个用户问题；官网承载什么基础事实；媒体稿怎样解释选择；哪些内容需要客户确认。法规、资质和行业承诺仅在实际适用且有依据时写。

### 4.3 内容创作机制与本案口径

保留素材表“内容类型 / 内容安排 / 需贵司提供的参考素材”。每类写具体选题、事实与案例依赖，不统一填“提供品牌资料”。

保留本案规范表，逐项给主体称谓、品牌与主体关系、域名与官方渠道、资质、服务/规模、收费与效果、同名实体和案例边界。写出能直接用于稿件的句式和待确认字段；没有事实时缩减断言，不暂停整套交付。

一篇稿件要围绕一个明确用户选择问题，提供适用条件、具体事实与可理解的选择理由。多篇必须在对象、比较标准、地域案例或决策阶段有差异，不把相同宣传稿改标题算多篇原创。

### 4.4 阶段计划与长期维护

保留三阶段思路：先统一事实与基础信任，再建设推荐/决策场景，最后收口与维护。阶段表保留原七栏“阶段 / 周次范围 / 阶段核心目标 / 周度固定发文量 / 本阶段产出稿件 / 服务商刚性交付指标 / AI效果目标”。

先排逐篇内容和具体媒体，再汇总阶段篇数与周频。频次不均时写区间或周明细，不能将每周3—4篇套到实际上只发2篇的阶段。

周期先遵守用户或素材明确要求。年度方案须覆盖整个年度和各自然季度，不能只有前两个季度的任务；可以前期集中建设、后期维护，但后期的实际内容、媒体、日期、数量与已计费用必须落表。短期项目可沿用原模板的启动周期，不能擅自把短期报价称全年服务。

维护表保留“后续阶段 / 安排与调整方式 / 频次”，按需说明回答观察、事实更新、补充内容、需求扩展、竞品变化、素材协作、错误纠偏和阶段调整。标清哪些已经列入本期预算，哪些只是另期建议，不承诺一次费用无限期维护。

### 4.5 媒体构成与费用预估

先说明媒体角色与内容分工，再列真实媒体、价格、数量和费用。原模板只给媒体类型的地方，本skill必须进一步从内置目录选出实际资源。门户名前缀、账号名称或报价档位不等于央媒身份、独立编辑背书或AI友好认证。

公共报价日期、市场参考价口径、税费与服务范围集中说明一次。媒体明细用于比较具体资源与文章，避免每条单价下复制同一大段免责声明。

费用按下一节编排。封面总额、阶段/季度费用、客户Excel与推荐媒体Word同源，不手抄另一套总价。

### 4.6 客户侧配合与实体区隔

保留“配合动作 / 说明 / 优先级”。每项说明做到什么：页面放在哪、包含哪些字段、谁提供事实、在什么阶段之前完成、对应哪篇稿件或检查点。客户自有动作与媒体投放数量分开，不重复计费。

确有同名、历史主体或关联品牌理解混淆时，再写“路径 / 核心操作 / 优先级”区隔表。事实尚未确认时说明需要统一的关系，不把错误归因或负面指控写成已证事实。

### 4.7 目标场景与差异化内容清单

保留核心场景的“场景分组 / 问句清单”，以及“具体问句 / AI当前说法、本品牌差异、补位方向”的逐问句说明。平台差异只在实际存在时写，未回传平台不新增样本结果。

对明确不适配的需求说明业务边界；不用虚构竞品弱点、夸大资质或保证推荐效果创造差异化。诊断中推荐的标签和内容机会必须在这里和排期中找到落点。

### 4.8 附：发文排期明细

平台型保留原十列“周次 / 信源层 / 媒体类型 / 内容形态 / 拟发标题 / 平台 / 观察端口 / 对应目标问句 / 核心卖点或可核验事实 / 节点”。服务型保留其原九列“周次 / 信源层 / 具体媒体 / 内容形态 / 拟发标题 / 平台 / 对应目标问句 / 核心卖点或可核验事实 / 检查节点”。以所选profile的原表头为准。观察端口按本轮实际网页范围，不凭文章形态推断APP/Web抓取路由。

### 4.9 预期效果与方案口径

分别给可承诺交付、传播覆盖的合理方向、AI表现希望改善的具体场景。每项效果对应内容任务、阶段和观察点。没有历史曝光或转化数据时不给虚构数值，也不只写一句“效果不保证”代替预期分析。

写明媒体刊发完成、搜索可见、AI提及、来源引用、有效咨询是不同结果。引用/排名变化可作为观察目标，不能被固定刊发量保证。最后核对范围、数量、周期、维护和费用边界，不用“以正文为准”掩盖封面残留旧数。

## 5. 约2万元预算如何编排

### 5.1 先把预算放进项目，不沿用旧null

优先读取本轮对话，再读客户表和旧project。明确目标写 `budget_target`，上限写 `budget_limit`。本skill当前默认建议目标为20,000元，上限20,000元；只有用户明确给了不同预算才覆盖，不能把旧项目的null视为允许任意小包。

预算目标是建议执行规模，不是已经确认的结算承诺。约2万元的完整建议包，已知费用应在18,000—20,000元附近；单独2,000元的小包不能当这项任务完成。明确只给费用上限、允许少花的客户，则按该明确约束执行，不擅自强制花满。

### 5.2 按内容与媒体角色配置，不按最低价排序拣几家

1. 把诊断优先问题分配到基础事实、需求推荐、决策说明、地域/行业案例和持续维护。
2. 按每类内容的作用查真实资源：重点品牌事实与适配的主流承载、行业专业解释、属地/场景、目标人群常用平台。角色可合并，不强求每类配额。
3. 分价格区间查询候选，既查适配的重点媒体，也查中价专业/地方资源和补充平台。`media.py --min-price/--max-price`用于扩大可选择的层次；仍按业务、题材限制和刊发形态筛选。
4. 选定具体文章、媒体、次数与日期后，以原目录市场参考价或已有明确对客报价计算。金额不够时检查遗漏的需求、内容差异、媒体层次和全年维护，而不是给同一稿机械增加十倍发布。
5. 超出目标时按业务优先级优化资源和篇目，保留必须的事实与关键需求，重新计算。

不靠提高目录单价、无依据服务费、补差额、虚构“优化管理费”或重复算一项任务凑到2万元。可用资源与题材确有限制时，在方案里说明具体取舍，内部继续配置有依据的任务；不能直接把两千元的零散投放包交为正式年度方案。

### 5.3 费用逐项可复算

市场参考价填 `market_reference_price`，需要形成对客建议预算时同值填 `client_unit_price`，标明市场参考价与报价日期；内部 `unit_price` 未知仍为null。已确认客户售价优先于市场参考价，不擅自折扣或加价。

媒体费=各实际刊发的单价×次数；其他费用仅使用已有明确服务范围和报价。写稿、建设页面、复测等缺报价时，说明未计入该媒体包或另行报价，不能把媒体包冒充含全部服务。客户要求综合总预算时，应从总目标中为已知服务费用留空间，而不是媒体先花满再附加收费。

汇总至少对齐：目标/上限、已知媒体费、已知其他费、已知合计、未计服务边界、阶段和自然季度金额。原参考的总价或档位不能直接抄到新项目。
