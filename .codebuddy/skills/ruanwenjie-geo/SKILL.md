# 软文街 GEO 诊断与执行规划

WorkBuddy负责客户资料整理、问题设计和工具编排；本地MCP调用gpt-6.1-sol（API推理max，上下文窗口1,050,000 tokens）负责回答判读、分析、成稿及终审。交付两份：GEO诊断报告.pdf和品牌传播与GEO执行方案.pdf。不检索或推荐具体媒体，不生成推荐媒体.xlsx；历史客户文件、候选和旧成果均保留。

## 本地GPT接入与付费边界

收到回答后先读[本地MCP安装与执行](references/local-mcp.md)，调用geo_status确认配置。使用完整原答和全部可定位截图，API请求由工具加载业务规则。密钥缺失或调用失败时报告具体问题，不能自行起草冒称GPT完成。

生成请求以后台任务提交并保存response_id。pending仅表示已提交，每15至30秒调用geo_resume_task(run_dir)查询同一任务；只有status=completed且对应业务产物齐备才推进。失败、过期、状态未知或没有ID时停止，不能自动新POST。失败方案只有用户明确授权新的付费请求，且调用geo_create_plan时传入与原失败检查点完全一致的retry_failed_response_id，才可在同一run创建新任务；保留旧记录。等待中的任务不得借此重试。

已有analysis.json、model-analysis.json和judged.xlsx的旧run直接复用，不重跑分析或媒体检索。不要传候选文件。旧版含具体媒体的计划或草稿不能作为新版分类方案直接发布，须保留旧结果并明确生成新版方案。

两份报告先留客户.work。geo_review_deliverables读取实际17页图片并与逐页原模板比较，检查事实、分类报价和分工。终审status=completed且passed=true、成品哈希未变时才能geo_publish；按意见修正并复审最多两轮，仍不通过时保留草稿和问题。审核记录仅留内部。

## 收到回答后的执行顺序

1. **找出选择差距。**按[本地MCP执行](references/local-mcp.md)导入完整原答并调用geo_analyze_customer；结合实际品牌印象、同行选择理由和客户真实优势，判断选择差距。仅分析已收到回答的平台。
2. **确定场景与内容。**优先有业务价值且事实可支撑的场景，明确适合谁、解决什么难点、凭什么选择本品牌。主体与售后说明可并行补强；合规是信任条件，不默认代替核心获客业务。
3. **生成分类计划。**调用geo_create_plan(run_dir)，不检索或传媒体候选。按权威媒体、行业媒体、自媒体三类安排用途和计划刊次；只计算普通、高权重两档分类报价，不列媒体名称、账号、栏目，不虚构采购成本。
4. **核费用与分工。**两档同内容、独立稿数及每稿刊次；每档计划媒体费最低12,000元，写作另收费。意向预算仅供参考，客户明确不能超过时才作为媒体加写作总额硬上限。具体资源、刊发条件与两档实际权益差异均待确认，不得当作已落实或保证效果。
5. **客户成稿。**geo_write_reports依据[固定页式生成说明](references/template-generation.md)生成两PDF，写本品牌现状、同行差异、选择理由、场景、双方动作和费用。原答、内部编号、制作指令和核算留.work。
6. **独立终审和交付。**geo_review_deliverables逐页检查诊断8页及执行9页；终审通过后geo_publish只交两PDF。真实调用、模拟测试及WorkBuddy界面验收分别报告。

## 交付与事实边界

- 只有客户资料时，读[客户输入与问题设计](references/workflow.md)，按实际采购判断生成“问题、引用截图、答案”三列人工采集表，不设固定数量。
- 截图无完整URL仍分析可见标题、站点和来源结构；不补未调查的平台或未经核实的事实。项目日期未确认时，若使用示例日历，须在客户方案明确标为待双方确认。
- 诊断保留同行与自身比较、四列冲突表和双方分工；执行保留同行差异、四步2×2、三类媒体三卡、复核三列表和两档报价。固定背景、坐标与字号不得为绕过溢出而修改；文字过长时精简后重导。
- 媒体费已含的服务、写作费用和客户分工须同源。新增收费服务先明确范围与价格；客户负责事实审核、官方载体操作和实际争议处理。
- 内容组、阶段、三类计划刊次和两档费用同源；逐页检查17页的文字、标题、表格、费用、溢出、遮挡和旧案例残留。模型通过不替代本地可见成品检查。
- 原件和旧成品保留；内部project、analysis、plan、判读、证据和核算放客户.work。客户数据不得上传公开仓库；不自动采集、监测、下单或发布媒体。
