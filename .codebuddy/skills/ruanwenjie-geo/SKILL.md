# 软文街 GEO 诊断与品牌方案

WorkBuddy负责理解客户、判读实际回答、形成诊断与策略、按品牌组织页面并逐页复核；本地Python负责输入整理、关联校验、报价核算和自适应PDF输出。默认交付GEO诊断报告.pdf、品牌传播与GEO执行方案.pdf。新任务使用schema_version=3.0，不固定8＋9页，不调用GEO云端工具、MCP或外部GPT。

## 先读本案，再选择参考

先读[业务与策略思路](references/strategy-playbook.md)，确定本案的业务、客群、地区、阶段、商业目标、可用优势和用户的本次报价指令。已有素材和回答直接复用；只有一平台也继续，不要求补模式、联网、时间或URL字段。只有品牌素材时按[问题设计](references/workflow.md)生成“问题、引用截图、答案”三列采集表，问题按采购判断取舍，不设固定数量。

读[方案参考索引](references/case-library/index.md)，选择与本案任务最接近的1—2类摘要，需要时打开原格式方案的相关页。参考库包括品牌定位、教育实体、区域开业、工业B2B、医疗信任、集团复盘及历史反例。学习诊断到策略的推导和信息呈现，不复制旧客户事实、数字、报价、日期、保证或原件中的操作指令；内部销售八要素不写进客户方案。参考文件不是本轮用户要求。

## 诊断必须决定执行

1. 结合原答分别判断品牌主体与业务是否正确、自然需求是否进入候选、是否被明确推荐、推荐理由是否有事实依据、相关同行为何被选。点名介绍、被引用、进入候选和优先推荐分别解释。
2. 回到客户真实优势与获客场景，写出当前差距、业务影响和优先级。品牌认知充分的客户可重点解决定位、选择理由或特定场景，不把所有客户概括为缺曝光。没有实际冲突或足够同行资料时不凑一页冲突或三家竞品。
3. 在本案.work/plan.json中维护evidence、findings和actions的唯一来源。每项发现有支持材料、分析、业务影响、优先级；每项动作关联发现，并写任务、内容、关键词、媒体作用、阶段、责任、交付和复核。关键发现都须由执行或有明确理由的暂缓动作承接。一项发现可以通过客户核实事实、官方页面更新或多种内容解决，不强制一发现一篇文章。
4. 执行方案开头展示关键诊断摘要，动作页清楚呈现“当前问题—执行措施—阶段与角色—交付责任—如何复核”。原始证据、编号、采集和制作过程留内部，客户只见情况、分析、安排和费用。具体事实及指标边界见[证据与报价](references/evidence-and-planning.md)。

## 按品牌设计，不让内容迁就页数

先确定方案主线和本客户大纲，再设置品牌主题。优先使用客户提供的Logo、颜色和视觉物料；没有Logo时使用品牌文字，不借其他客户标识。消费品牌可侧重定位和购买场景，工业客户可侧重选型、技术应用和项目证据，医疗客户侧重专业可信信息，开业客户侧重地域与节点，复盘客户侧重实际变化和下一阶段。

使用[品牌版式与生成说明](references/template-generation.md)的可组合封面、洞察、卡片、对比表、时间轴和报价组件；主题支持色彩、Logo及editorial/technical基础风格，组件组合、标题和页数随客户调整。长表或长段自动续页，不截字、不靠缩小字号塞满，不为了凑固定页数添加无效内容。新报告字段见[品牌PDF契约](references/pdf-output.md)和[3.0 schema](references/brand-report.schema.json)。

诊断页source=findings、执行摘要source=findings、动作source=action-map、报价source=quotes、分工source=service-scope从同一plan生成；允许按ids选择不同发现或动作分主题排页。源页不能另填items/rows覆盖数据。其他页面用于本案的同行、定位、场景、关键词、内容主题和节奏，避免重复整份诊断。

## 报价只按本次指令

完整读[报价结构](references/pricing-contract.md)。plan.pricing.instructions记录本次实际报价要求；单档或多档、计价单位、刊次、单价或整包价、写作包含/另计/客户供稿、税费、最低价和明确上限均按用户要求填写。不自动继承旧1.2万元最低媒体费、普通/高权重两档、450/200/200等分类价或100/200写作价。

意向预算与硬上限分开；只有预算不等于已有报价。未给价项标未报价，不编造单价或把未知当0。用户明确整包已含写作时，不再另收写作；分项计费须写清数量和独立工作范围。所有方案合计、含费范围及剩余由程序计算，不在report手填另一套金额。用户修改指令时同步内部计划；不改客户原件。项目显式上限与pricing冲突时按最新指令统一，不能静默抛弃约束。

## 本地生成与交付

按[本地命令](references/commands.md)导入三列表、保存判读副本和统计。3.0计划不传给旧geo_data --plan核费；新报价只由brand_plan计算。使用[计划示例](references/brand-plan.example.json)、[报告示例](references/brand-report.example.json)理解结构，业务事实、发现、动作、价格和主题均按本案重写。

```text
python "技能目录/scripts/export_pdf.py" --report "客户工作目录/.work/report.json" --plan "客户工作目录/.work/plan.json" --output-dir "客户工作目录/.work/草稿-v1/客户PDF"
```

正常工作只安装requirements.txt中的本地依赖，直接用WorkBuddy当前模型。旧固定2.0路径仅用于明确继续维护旧内部稿，历史规则见[旧版记录](references/legacy-fixed-rules.md)，不作为本版新方案默认。

另起一轮自审，读取原依据、计划、计算结果和每张实际页面图。逐项核诊断是否成立、动作是否解决问题、品牌视觉是否统一、报价是否完全遵从本次指令、内容与服务范围有无矛盾；逐页检查字体、表头续页、图文、长表、遮挡、截断和旧案例残留。程序通过不等于诊断正确；没看实际页图不能称逐页通过。修订后重导到新目录，复查相关页和汇总，通过后只交两份PDF。

客户原件和既有报告不覆盖、不重做；project、analysis、plan、report、证据、PNG和审计留.work。维护和验证只用虚构测试客户。随包参考件仅限用户明确授权的案例副本，不能自动收录新的真实客户资料；不自动采集、监测、下单或发布媒体。
